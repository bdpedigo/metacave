# Long-Term Table Access & Feature Sets — Design Brainstorm

**Date:** 2026-04-06  
**Status:** Option B (new catalog service) chosen; other options retained for context

---

## Problem Summary

Two related capability gaps share the same three sub-problems.

### Gap 1 — Long-term / quarterly materialization dumps
- MaterializationEngine creates time-locked snapshots but the "long-term" quarterly ones are currently dumped as gzipped CSVs into a GCS bucket.
- **Discoverability:** no documented or machine-readable way to know these exist.
- **Access control:** bucket-level only; no CAVE auth integration.
- **Partial query:** impossible to retrieve a subset of a 10s-of-GB table without downloading all of it.

### Gap 2 — Feature sets (morphology embeddings, etc.)
- Data scientists generate feature tables (embeddings, morphology descriptors) keyed to PCG root IDs.
- Computed on intermittent schedules; may not exist for every materialization version.
- Same discoverability, access control, and partial-query problems as Gap 1, with the additional concern that they are not "annotations" and don't belong in AnnotationEngine.

---

## Cross-Cutting Structure

Both gaps share identical sub-problems and both need to be **linked to a specific materialization version**. A single design layer — a *catalog* — can serve both.

---

## Idea 1 — Metadata registry: extend AnnotationFrameworkInfoService or add a catalog service

AnnotationFrameworkInfoService already acts as the "what exists and where" registry for datastacks. Two options are considered below, plus a middle path.

### Option A — Extend AnnotationFrameworkInfoService

**What this means concretely:** Add new DB tables and API endpoints to AnnotationFrameworkInfoService for `table_archive` and `feature_set` resource types, each record containing:
- Datastack name
- Materialization version (FK to ME version)
- Storage format (`iceberg`, `delta`, `lance`)
- Bucket path / catalog URI
- Column schema (name, type, semantic role)
- Joinable key columns (e.g. `root_id`, `pt_supervoxel_id`)

**Data model tension:** AnnotationFrameworkInfoService currently stores flat config — service URLs, aligned volume descriptors, permission group names. A catalog record is structurally different: it's versioned, has a variable-length column schema, carries lineage pointers, and will accumulate many records per datastack over time. Cramming this into AnnotationFrameworkInfoService either requires significant schema complexity in a service that was never designed for it, or forces a shallow representation that loses valuable metadata.

**Permission model fit:** AnnotationFrameworkInfoService manages permissions at the *datastack* level, delegating to middle_auth permission groups. A catalog may need finer-grained control — e.g., a feature set generated by an external lab is accessible to some users but not others within the same datastack. This is harder to express cleanly in AnnotationFrameworkInfoService's current model.

**Write path question:** Who registers a new table or feature set? If external pipelines (Celery jobs, data scientist scripts) POST registration requests, AnnotationFrameworkInfoService becomes a write target for compute jobs, not just an admin-edited config store. That's a shift in the service's threat model and operational profile.

**Upside:** Fastest path to a working system. CAVEclient already has an `info` sub-client; `client.info.get_tables()` could be added quickly. No new Helm chart, no new deployment config.

---

### Option B — New lightweight catalog service (chosen option)

**What this means concretely:** A new Flask service backed by Postgres, following the standard CAVE service pattern (middle_auth_client for auth, CAVEclient sub-client wrapper). It owns catalog records exclusively and can evolve its schema independently of AnnotationFrameworkInfoService.

**Clean data model:** The catalog service can be designed from the start around versioned records, column-level metadata, lineage DAGs, and per-resource permission overrides — none of which fit naturally in AnnotationFrameworkInfoService's config-oriented schema.

**Ownership and evolution:** Feature sets come from many sources (different labs, different pipelines). A dedicated service gives external contributors a clean, well-scoped API to register and describe their outputs without needing access to the core info service. It can also absorb adjacent responsibilities over time (e.g., triggering export jobs, tracking compute provenance) without polluting AnnotationFrameworkInfoService.

**Permission granularity:** A standalone service can implement per-catalog-record ACLs backed by middle_auth groups, without being constrained by AnnotationFrameworkInfoService's existing permission model.

**Cost:** A new service means a new Helm chart, Docker image, Postgres database (or schema), and CAVEdeployment/terraform-google-cave additions. For a team already maintaining many services, this is real overhead.

---

### Option C — AnnotationFrameworkInfoService with a clean internal module boundary (middle path)

Implement the catalog logic as a self-contained Flask Blueprint inside AnnotationFrameworkInfoService, with its own DB models, migrations, and route prefix (e.g. `/catalog/v1/`). This buys Option A's deployment simplicity now while preserving the ability to extract it into Option B later — the blueprint can be physically moved to a new repo once the API stabilizes and the operational cost of a new service is justified.

**Risk:** "We'll extract it later" often doesn't happen. The module boundary must be enforced deliberately (no shared DB models, no shared business logic with the rest of AnnotationFrameworkInfoService).

---

### Summary comparison

| Dimension | Option A (extend AFIS) | Option B (new service) | Option C (blueprint) |
|-----------|----------------------|----------------------|----------------------|
| Time to ship | Fastest | Slowest | Fast |
| Data model fit | Poor | Good | Good |
| Permission granularity | Limited | Full | Full |
| Write-path safety | Low (AFIS becomes a compute target) | High | Medium |
| Deployment overhead | None | High | None |
| Future extractability | Hard | N/A | Medium |

**Decision: Option B.** A new standalone catalog service provides the right data model, permission granularity, and write-path isolation for both long-term table dumps and feature sets.

## Idea 2 — Access control: proxy the credential, not the data

For tables that are 10s of GB, don't route data through a CAVE service. Instead, after verifying the user against middle_auth, the catalog service issues **short-lived signed URLs or STS/Workload Identity credentials** scoped to the relevant bucket prefix. The user then queries Iceberg/Delta/Lance directly from their local environment (DuckDB, Polars, PyIceberg, etc.).

This keeps the hot path serverless while still enforcing auth. Mirrors how NeuroglancerJsonServer handles state access — the service controls metadata and auth; the heavy payload comes straight from cloud storage.

---

## Idea 3 — Partial query format

| Format | Best for | Notes |
|--------|----------|-------|
| **Apache Iceberg** | Long-term mat dumps | Broadest tooling (DuckDB, Spark, BigQuery external tables, Polars, PyIceberg); strong partition pruning; column stats in metadata. Partition by root ID range or timestamp. |
| **Delta Lake** | Alternative to Iceberg | Similar capabilities; more Databricks-centric ecosystem. |
| **Lance** | Feature sets / embeddings | Native ANN (approximate nearest-neighbor) index support; better for vector workloads. |

Suggested split:
- **Long-term mat dumps → Iceberg** (parquet-snappy, partitioned by root ID range)
- **Feature sets → Lance** if ANN queries are needed; Iceberg if purely flat-tabular

## Idea 4 — Schema advertisement and linking

Iceberg table metadata (`.metadata.json`) already carries column names, types, and partition specs. The catalog service would add a **semantic role** field per column:

| Column name | Semantic role |
|-------------|---------------|
| `root_id` | PCG root ID join key |
| `pt_supervoxel_id` | supervoxel |
| `pt_position` | spatial coordinate |
| *(arbitrary)* | feature / embedding |

This mirrors what EMAnnotationSchemas already does for annotation columns. The catalog could lean on EMAS types for known columns and allow arbitrary extras for embeddings.

Each catalog record also stores a **lineage pointer**: which ME materialization version it was derived from, and (for feature sets) which script/model version produced it.

---

## Idea 5 — CAVEclient integration

A new `client.catalog` (or `client.tables`) sub-client:

1. **List** available long-term versions and feature sets for a datastack.
2. **Describe** a specific table: format, columns, semantic roles, mat version, coverage.
3. **Open** — returns a connection config (signed URL / PyIceberg `Catalog` params / Lance URI) so the user can do:
   ```python
   tbl = client.catalog.open("flywire_783", "synapses", version="2025-Q4")
   # returns a PyIceberg Table, Lance Dataset, or similar
   df = tbl.to_pandas(filter=pc.field("root_id").isin(my_ids))
   ```
4. **Thin query helper** for the common pattern: "give me all rows for these root IDs."

## What's New vs. What's Reused

| Need | Reuse | New |
|------|-------|-----|
| Auth enforcement | middle_auth + middle_auth_client | — |
| Discoverability | AnnotationFrameworkInfoService (extended) or new catalog service | New catalog endpoints / resource types |
| Schema metadata | EMAS column type vocabulary | Catalog schema registry |
| Partial query | — | Iceberg/Lance tables on GCS + signed-URL issuance |
| CAVEclient access | Existing sub-client pattern | `client.catalog` sub-client |
| Mat version linking | ME version IDs | FK in catalog records |

## Open Questions

- How are feature sets versioned when their computation schedule doesn't align with ME mat versions? (Pin to nearest mat version? Store independently with a timestamp?)
- Should the catalog service drive *writing* the Iceberg/Lance tables (i.e., trigger the dump/export job), or only *register* tables that were written externally?
- Iceberg requires a catalog backend (Hive metastore, REST catalog, Glue, etc.) — do we self-host a REST catalog or rely on GCS-backed file I/O catalog (simpler but less capable)?
